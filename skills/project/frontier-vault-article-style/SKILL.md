# Frontier Vault 文章写作与渐进式阅读规范

## 0. Skill 定位

### 0.1 唯一服务对象

本 Skill 仅用于 `frontier-vault` 仓库中正式中文长文的：

- 新建；
- 补全；
- 重写；
- 风格审查；
- 内容迁移。

不用于参考项目、首页、模块索引、README、项目治理文档、脚本、配置或纯视觉调整。

### 0.2 内容库目标与读者

Frontier Vault 是面向**中高级前端工程师**的系统化知识库，覆盖浏览器底层原理、JavaScript 运行时、框架生态、性能优化、测试、AI 与职业成长，目标是帮助读者建立可落地的工程认知体系。

默认读者：

- 已掌握前端基础语法和常见框架用法；
- 能阅读代码、规范和性能面板；
- 希望理解机制、边界与工程取舍；
- 不需要教科书式铺垫，但需要关键概念被准确解释。

写作不得把读者当初学者逐词教学，也不得假设读者已经掌握文章要证明的核心机制。

### 0.3 核心写作目标

文章应同时做到：

1. **读得进去**：开篇快速建立问题与收益，章节有清晰推进，不用大段背景拖延结论。
2. **看得明白**：先建立直觉，再解释机制；新术语及时解释，复杂链路有图、例子或分步说明。
3. **记得住**：每章只承担一个核心认知变化，用小结固定关键判断，不机械重复原句。
4. **用得上**：事实可验证，建议有条件，方案说明收益、代价和适用边界。
5. **查得到**：标题、目录、术语和 FAQ 便于定位，但不为形式完整强行添加内容。

## 1. 基于仓库实际情况的强制约束

### 1.1 项目事实

执行任务时，应以仓库当前实现为准，并先核查以下事实是否仍成立：

- 站点使用 VitePress，中文文章位于 `docs/<module>/`，英文对应文章位于 `docs/en/<module>/`；
- 中英文文章使用相同英文 slug，形成一一对应关系；
- 内容按 browser、javascript、frameworks、performance、testing、ai、career 等模块组织；
- 文章属于 20 分钟以上的系统化长文，应覆盖原理、机制、工程实践与可执行结论；
- Mermaid 由项目主题自定义集成，支持五色语义、放大和明暗主题；
- 侧边栏及多语言配置由数据源和脚本生成，不能直接修改生成物 `docs/.vitepress/config.js`；
- 项目中的文章数、图表数、Skill 数量、版本号等数字会变化，引用前必须通过仓库命令重新统计。

这些是执行时必须复核的项目事实，不是永久不变的常量。仓库实现发生变化时，以实际文件和可复现验证为准。

### 1.2 文档事实的证据等级

文章中的事实按以下优先级取证：

1. 规范、官方文档、官方源码和项目实际实现；
2. 可复现的本地实测、构建产物和运行结果；
3. 可信的一手技术资料；
4. 项目既有文档；
5. 作者经验与推断。

项目既有文档可能过期，不能用一份文档去直接“纠正”另一份文档。涉及配置行为、默认值、部署现状、云环境和第三方服务状态时，必须检查实现、控制台、API 或实际响应。

### 1.3 验证结论必须验证判据

在写下“存在”“不存在”“已生效”“已通过”“数量为 N”等结论前：

- 先确认搜索命令没有漏掉隐藏目录；
- 计数模式必须排除子串误命中；
- 正则必须用已知样本反向验证；
- 生成器修改后必须检查生成物；
- 构建成功后必须检查最终产物或页面行为；
- 异常结果优先用第二种独立方法复核；
- CI 绿灯、命令退出码和 dry-run 成功都不能单独证明目标已达成。

文章若提供验证命令，还要说明：验证对象、期望信号、失败信号，以及该判据可能产生的假阳性或假阴性。

### 1.4 内容安全

公开文章、代码示例和命令输出不得包含真实公网 IP、邮箱、密钥、Token、个人路径或其他敏感信息。使用 `<ORIGIN_IP>`、`<TOKEN>`、`<USER_HOME>` 等语义明确的占位符。不得为了“真实感”保留生产凭证或个人信息。

## 2. 使用前必须读取的项目约束

修改文章前，读取并遵守：

- 根目录 `README.md`；
- `project-docs/CONVENTIONS.md`；
- `project-docs/CONTRIBUTING-i18n.md`；
- 目标文章；
- 同目录中主题最接近的 1 至 2 篇正式文章。

如果文件不存在，先报告缺失项，再基于可获得的约束继续；不得虚构规则。

冲突优先级从高到低：

1. 用户当前任务的明确要求；
2. Frontier Vault 项目级强制规范；
3. 技术事实与内容准确性；
4. 目标读者和文章目的；
5. 当前文章类型的专用规则；
6. 本 Skill 的表达规则；
7. 历史文章的既有习惯。

历史写法只能作为参考，不能自动视为正确规范。

## 3. 先判断文章任务，不要先套模板

### 2.1 文章类型

#### 原理型

识别信号：回答“它如何运行”“为什么会这样”。

常见主题：浏览器渲染、事件循环、GC、框架调度、编译过程。

主线：**现象或问题 → 直觉模型 → 机制链路 → 边界与反例 → 工程影响**。

#### 实践型

识别信号：回答“如何解决”“如何验证”“如何选方案”。

常见主题：性能优化、测试、迁移、工程流程、排障。

主线：**症状与目标 → 基线 → 方案 → 实施 → 验证 → 代价与回退**。

#### 决策型

识别信号：回答“应该选什么”“在什么条件下选”。

常见主题：框架选型、架构取舍、技术债治理、能力成长。

主线：**决策背景 → 评价维度 → 方案比较 → 约束与风险 → 条件化建议**。

一篇文章可以混合类型，但必须指定一个主类型。混合内容服务主线，不能并列堆放。

### 2.2 写作前先形成最小文章契约

动笔前用不超过 6 行明确：

- 目标读者当前知道什么；
- 读者面临什么问题；
- 文章只解决什么，不解决什么；
- 核心判断是什么；
- 读完后读者能解释、判断或完成什么；
- 需要哪些证据验证。

若无法写清这 6 项，先缩小主题，不要直接扩写成长文。

## 4. 长文的渐进式解释模型

复杂主题默认按以下认知顺序组织，而不是直接倾倒完整细节：

### 第 1 层：问题与直觉

先回答：

- 为什么值得读；
- 常见理解哪里不够准确；
- 可以先用什么简单模型理解。

这一层应让读者在不知道底层细节时也能跟上。

### 第 2 层：最小机制

只引入理解主线所必需的概念、角色和步骤。每新增一个术语，都要说明它在当前链路中的作用。

### 第 3 层：完整链路

展开时按因果或时间顺序组织。复杂链路优先使用：

- 编号步骤；
- 时序图或流程图；
- 输入、处理、输出；
- 触发条件、状态变化、结果。

### 第 4 层：边界与反例

说明简单模型在哪些情况下失效，包括：

- 浏览器或运行时差异；
- 版本差异；
- 数据规模变化；
- 缓存、并发或异步带来的例外；
- 为教学而简化的部分。

### 第 5 层：工程落地

把机制映射到可观察信号和行动：

- 在 DevTools、日志或指标中能看到什么；
- 如何验证判断；
- 可以采取什么措施；
- 收益、代价和适用条件是什么。

不是每篇文章都必须写满五层，但不得跳过读者理解当前层所需的前置阶梯。

## 5. 信息密度与阅读节奏

### 4.1 一段只推进一个意思

- 普通段落建议 1 至 4 句；
- 一个段落只完成解释、举例、转折或结论中的一个主要动作；
- 连续超过 5 句时，检查是否可拆成“判断 + 解释”“机制 + 影响”或列表；
- 不为追求短段落把完整逻辑切成碎片。

### 4.2 一节只承担一个核心问题

章节标题应能转化为一个明确问题。若一节同时回答多个独立问题，应拆分；若两个小节各自只有一两句话，应合并。

推荐章节粒度：读者用 3 至 8 分钟能完成一个认知单元。不要以字数硬切章节。

### 4.3 控制术语引入速度

- 首次出现时用“中文名称（英文全称，缩写）”或项目惯用格式解释；
- 一个自然段避免集中引入多个未解释的新概念；
- 同一概念全文只使用一个主名称；
- 缩写较少出现时直接写全称，避免增加记忆负担；
- 已具备行业共识的基础术语无需重复科普。

### 4.4 使用导航句，但不要写流程播报

好的导航句说明逻辑关系：

- “要解释这次阻塞，先区分任务入队和任务执行。”
- “上一步处理了网络等待，接下来剩下的是主线程竞争。”

避免：

- “下面我们来看看……”
- “首先、其次、再次、最后……”连续套用；
- “本节将详细介绍……”却没有新增信息。

### 4.5 重点有层级

- 加粗用于关键判断、对比维度和易混淆边界；
- 同一屏幕不要处处加粗；
- 引用块用于关键主张或语境，不用于普通段落装饰；
- 提示容器按需使用，同类容器不连续堆叠。

## 6. 开篇：用最短路径建立阅读动机

### 5.1 必须完成的任务

开篇前 3 至 5 个自然段内说明（不要求逐项各占一段）：

1. 读者遇到的具体问题或认知误区；
2. 文章的核心判断；
3. 文章会沿什么主线解释；
4. 读完后能获得什么工程能力。

### 5.2 推荐结构

- H1 标题，全文唯一；
- 项目现有格式要求的元信息；
- 80 至 180 字的导语；
- 按项目统一风格添加 `::: info 核心判断`，但正文导语不得再次原句复述；若现有文章暂未使用容器，改造时应补齐或明确说明不适用原因；
- 目录按项目能力或文章长度决定，不手写可能失效的近似锚点。

### 5.3 禁止写法

- “随着前端技术的快速发展……”；
- 从行业历史开始，数段后才进入问题；
- 重复标题和 description；
- 一开始抛出大量术语、结论和路线图；
- 以“本文将全面、深入、系统地……”代替实际价值。

## 7. 正文：用问题驱动，而不是结构驱动

### 6.1 每节的最小闭环

每个主要章节应尽量形成：

1. **问题或判断**：这一节要修正什么认知；
2. **解释或证据**：机制、代码、图、数据或来源；
3. **工程含义**：它会影响什么；
4. **局部收束**：用一句话或短列表固定结论。

项目要求核心论点贯穿全文，但不等于逐字重复。较长章节使用 `::: tip 本节核心结论` 将本章发现映射回总论点；短章节可用一句自然收束。容器中的内容必须是本章新增判断，禁止复制开篇原句。

### 6.2 先给直觉，再给精确定义

面对抽象概念时：

1. 先用准确但简化的语言建立直觉；
2. 再给正式定义或模型；
3. 立即说明简化模型的边界。

类比只能帮助建立入口，不能代替机制说明。类比失真的地方必须指出。

### 6.3 示例必须承担解释任务

每个示例都要回答：

- 示例要证明什么；
- 读者应观察哪一行、哪个状态或哪个指标；
- 为什么结果支持前文判断；
- 真实项目中使用时有哪些差异。

删除只为“显得内容丰富”而存在的代码、图和表格。

### 6.4 表格使用条件

仅在需要比较至少两个对象和至少两个维度时使用表格，例如：

- 方案、收益、代价、适用场景；
- 症状、可能原因、验证方式；
- 参数、含义、默认值、影响。

线性步骤、长解释和代码不要塞入表格。

## 8. 技术准确性与可验证性

### 7.1 区分事实、判断和建议

- **事实**：给出官方文档、规范、源码、实测或可复现证据；
- **判断**：说明成立条件和推理链；
- **建议**：说明适用场景、收益、代价和不适用情况。

不得把经验判断写成普遍事实。

### 7.2 代码与运行结果

- 代码块必须有语言标签；
- 仅保留支撑当前问题的必要上下文；
- 反例与正例仅在确有对照价值时成对出现；
- 写明关键环境、版本、命令或复现步骤；
- 输出、性能数字和截图结论必须来自真实运行或实测；
- 无法运行时明确标注“未在当前环境验证”，不得补写猜测结果；
- 不使用伪代码冒充可运行代码。

### 7.3 性能内容

性能结论至少说明：

- 测量对象；
- 环境与版本；
- 数据规模或样本；
- 测量工具与方法；
- 基线和对比方案；
- 结果波动或限制。

没有测量条件的精确数字应删除或改成定性描述。

### 7.4 来源

- 优先规范、官方文档、标准组织、项目源码与维护者资料；
- 来源必须真实可访问，并直接支持相关结论；
- 不用一条链接支撑整段多个不同结论；
- 无法确认的外部事实标记为待核实，不编造来源。

---

## 9. 图表与 Mermaid

图表只用于表达文字不易快速呈现的结构关系：

- 时间顺序；
- 因果链；
- 状态转换；
- 模块关系；
- 决策路径。

没有结构关系时，不强行添加 Mermaid。

若项目现有规范定义了 Mermaid 主题、配色和字体，必须复用；否则先读取同目录文章和项目配置，不在本 Skill 中重复硬编码易失效的视觉值。

图后必须有 1 至 3 句解读，告诉读者从哪里看、关键转折是什么。图不能代替正文解释。

## 10. Frontmatter 与项目格式

Frontmatter、分类、标签、阅读时间、标题锚点、国际化和内链规则以 Frontier Vault 当前项目文件及同目录正式文章为准。

执行时：

- 保留项目已有字段及顺序；
- 不从参考项目迁移治理字段；
- `readingTime` 按项目现有计算方式生成或校验，不凭感觉虚标；
- 标题和目录锚点必须与构建后的实际 heading ID 一致；
- 修改中文文章时检查英文对应关系和链接影响。

若本 Skill 示例与仓库当前实现冲突，以仓库实现为准，并建议更新 Skill。

---

## 11. 收尾：完成认知闭环，不重复全文

### 10.1 结语

结语回答两个问题：

- 读者现在应如何重新理解主题；
- 下一步最值得做什么或观察什么。

建议 1 至 3 个短段落。不得逐章复述，不写“综上所述”，不机械第三次复制核心论点。

### 10.2 按需组件

以下内容均按文章价值决定，不是固定套餐：

- **实践清单**：实践型和包含工程建议的原理型文章默认使用；每项必须可执行、可观察或可验证，不能只是章节标题的改写；
- **决策清单**：决策型文章且读者需要现场判断时使用；
- **统一模型**：多个章节确实能归入同一模型时使用；
- **FAQ**：项目长文默认保留，但只收录正文未直接回答、读者高概率搜索或容易误解的问题，通常 3 至 5 个；若没有有效问题，允许省略并在审查结果中说明；
- **来源**：有外部事实、规范、数据或重要延伸阅读时使用，并遵循项目规定。

不得为了“结构完整”硬凑统一模型或 Mermaid。FAQ 与实践清单虽然是项目默认结构，但没有高价值内容时宁可省略并说明，也不能用重复内容凑数。

## 12. 去模板化与去 AI 味

删除或改写：

- 空泛开场和宏大背景；
- 没有信息增量的过渡句；
- 同一结论在开篇、章节和结语中原句重复；
- 每节固定出现相同容器、相同句式和相同节奏；
- “显而易见”“毫无疑问”“彻底解决”等无依据绝对化表达；
- 为覆盖关键词而堆砌术语；
- 为显得系统而过度分类；
- 为显得专业而使用不必要的抽象名词；
- “值得注意的是”“需要指出的是”等可直接删除的前缀。
- 章节结尾连续出现“核心结论 + 常见误区”，但两者只是复述正文；
- 用“会怎么挂”“拉胯”“裸奔上线”等强口语表达替代准确机制说明；可少量用于强调，但不能成为全文默认语气；
- 单独一行写“把 X 当作 Y”，却没有“误区：”标签、主语或解释，造成残句；
- 手写目录与实际标题锚点重复维护，导致标题修改后链接失效；
- 在一个超长主题中并列堆放多个体系，却没有说明它们之间的依赖关系和阅读路径；
- 示例数字、推荐参数或阈值没有环境、模型版本、数据集或来源。

优先使用具体主语和动词：

- 不写“进行性能方面的优化”，写“减少主线程长任务”；
- 不写“实现对状态的管理”，写“集中更新状态”；
- 不写“具有一定的局限性”，写清楚在哪个条件下失效。

## 13. 真实长文样本暴露出的重点审查项

审查 Frontier Vault 现有长文时，优先检查以下问题：

### 13.1 Frontmatter 与正文重复

Frontmatter 已提供 title、description、category、tags、readingTime 和 outline 时，正文不再重复“副标题 / 目标读者 / 阅读时间”元信息块，除非这些信息对理解文章有额外价值。H1 必须与项目的实际渲染约定一致，避免 Frontmatter title 与正文 H1 产生双标题。

### 13.2 超长主题的范围控制

如果一篇文章同时覆盖技术原理、测试方法、评估、安全和效率提升，必须给出总问题、模块关系和推荐阅读路径。不能只因为主题相关就将多个完整知识域并排拼接。无法形成单一主线时，优先拆成系列文章，并用总览文章连接。

### 13.3 核心论点不是重复口号

开篇、章节和结语可以呼应同一个核心论点，但三处承担不同职责：

- 开篇：提出需要证明的判断；
- 章节：增加局部证据或限制条件；
- 结语：给出经过全文论证后的工程判断。

三处原句相同，视为重复，不视为“贯穿”。

### 13.4 口语化的边界

允许自然、直接和少量口语化表达，但技术长文的默认语气应是“专业、清楚、不端着”。口语表达必须满足：不损害准确性、不贬低读者、不替代因果解释、不过度密集。

### 13.5 参数与数字

对于 temperature、top-p、p-value、并发量、窗口长度、性能收益等数字：

- 区分示例值、经验范围、默认值和硬性标准；
- 标明模型、版本、工具、样本或适用条件；
- 无法验证时改写为条件化建议，不保留伪精确数字；
- 项目统计数字必须附可复现统计方式。

### 13.6 Mermaid 语义

复用项目五色主题时，颜色必须表达稳定语义，而非只为画面丰富。图中节点命名应短、平行、可扫描；复杂图在正文先说明阅读方向，图后解释关键转折。不得在每张图中重复大段主题初始化配置，如果项目渲染层已经统一提供主题，应使用项目能力。

## 14. 新建文章流程

1. 确认目标文件属于 Frontier Vault 正式长文。
2. 读取项目约束和相邻文章。
3. 判断主文章类型。
4. 写出最小文章契约。
5. 列出 3 至 7 个核心问题，按读者认知依赖排序。
6. 为每个问题确定证据：机制、代码、图、实测或来源。
7. 先写最小机制主线，再补边界和工程落地。
8. 完成后删减重复解释、无效示例和模板化收尾。
9. 校验 frontmatter、术语、锚点、代码、链接、i18n 和构建。
10. 输出成稿以及未验证项。

---

## 15. 改造已有文章流程

### 13.1 先诊断，后改写

先输出简洁的改造摘要：

- 保留：准确事实、有效示例、重要链接和项目特有内容；
- 调整：结构、段落、术语、解释顺序和证据表达；
- 删除：重复、空泛、失实、失效或无助于主线的内容；
- 补充：缺失的前置概念、边界、验证和工程影响。

除非用户要求先审批计划，否则输出摘要后直接执行，不因低风险风格修改反复等待确认。

### 13.2 改造优先级

1. 修复事实与来源错误；
2. 恢复文章主线；
3. 调整解释顺序，使其由浅入深；
4. 删除重复和低信息密度内容；
5. 补足边界、示例与验证；
6. 统一术语和格式；
7. 最后处理语句润色。

不得借“润色”改变技术含义、项目定位或有效结论。

## 16. 审查输出格式

先给结论：`通过`、`需修改` 或 `阻塞`。

随后按严重度列出问题：

- **高**：事实错误、错误因果、代码不可用、来源失实、项目规则冲突；
- **中**：主线断裂、关键前置缺失、结构错位、建议无边界、重要术语混乱；
- **低**：段落过长、重复表达、模板化容器、低价值过渡、局部格式问题。

每个问题包含：

- 位置；
- 原文短句或现象；
- 风险；
- 最小修改建议；
- 是否需要实测或来源复核。

用户要求直接优化时，在审查后完成修改，不只给建议。

## 17. 质量检查清单

### 定位与结构

- [ ] 目标文件属于 Frontier Vault 正式长文；
- [ ] 主文章类型明确；
- [ ] 文章只围绕一个核心问题或判断展开；
- [ ] 章节顺序符合读者的认知依赖；
- [ ] 开篇在 3 至 5 段内说明问题、判断、主线和收益；
- [ ] 收尾组件按需选择，没有为了模板完整而硬凑。

### 可读性

- [ ] 先有直觉，再有机制，再有边界和工程落地；
- [ ] 每段主要表达一个意思；
- [ ] 每节解决一个清晰问题；
- [ ] 术语首次出现时解释，全文命名一致；
- [ ] 没有连续堆叠陌生概念；
- [ ] 导航句表达逻辑关系，不是流程播报；
- [ ] 没有同一句核心论点机械重复多次。

### 准确性与落地

- [ ] 事实、判断、建议已区分；
- [ ] 关键事实有来源、源码或实测；
- [ ] 代码示例有必要上下文和验证说明；
- [ ] 性能数字包含环境、方法和样本；
- [ ] 建议说明收益、代价、边界和不适用条件；
- [ ] 无法验证的内容已明确标注。

### 表达与格式

- [ ] 已删除空泛开场、机械过渡和重复总结；
- [ ] 图、表、代码都承担明确解释任务；
- [ ] 表格只用于多维比较；
- [ ] Mermaid 和 frontmatter 遵循仓库当前规范；
- [ ] 锚点、链接、i18n 和构建已检查；
- [ ] 没有写入参考项目的名称、路径、治理字段或专属模板。

## 18. 验证命令与结果

优先使用仓库现有命令验证，例如文档构建、文章审计、链接检查和 i18n 检查。具体命令必须从 `package.json`、脚本目录或项目文档读取，不凭记忆硬编码。

最终报告列出：

- 已运行的命令；
- 通过或失败结果；
- 未运行项及原因；
- 剩余风险。

不得把“未发现问题”写成“已验证通过”。

## 19. 禁止事项

- 将本 Skill 用于 Frontier Vault 之外的项目；
- 迁移参考项目的名称、路径、业务背景、治理字段或课程模板；
- 把所有文章强制套入同一章节结构；
- 强制每章添加提示容器，或强制每篇包含 Mermaid、FAQ、统一模型和实践清单；
- 为了简洁删除关键机制、限制条件或有效证据；
- 为了显得深入堆砌术语、源码细节和无关分支；
- 编造代码输出、性能数字、版本、来源或验证结果；
- 用修辞替代因果解释；
- 未读取项目约束就修改 frontmatter、链接、Mermaid 或 i18n；
- 只做语言润色，不检查事实、结构和工程边界。
